# @gekichumai/maimai-domain

Shared maimai DX domain logic for the DXRating web app and backend: the song catalog, sheet identity, Best 50
calculation, import normalizers and the cloud-save score rules (meta#17).

## Cloud-save score rules

| Module | What it holds |
|---|---|
| `src/achievement.ts` | `toAchievementInt` / `fromAchievementInt` / `formatAchievementInt`: achievements as integers in 1/10000 % |
| `src/score-provenance.ts` | zod enums and types: `ScoreSource` (+ `SERVER_IMPORT_SOURCES` / `CLIENT_IMPORT_SOURCES`), `FetchedBy`, `Verification`, `EntryMethod`, `ManualEntryMethod`, `SourceAccountKind`, `ImportTrigger`, `ProvenanceSchema` |
| `src/score-merge.ts` | `compareScore`, `decideImportMerge` (§5.3), `manualVerification` and `decideManualMutation` (§5.4) |
| `src/import-normalizers.ts` | `withAchievementInt` / `ratingEntryAchievementInt` add integer achievements to normalizer results |

The decision functions are pure: they take the stored record (or `null`) and return what to write, whether the
row gets a new revision and which event to log. The server applies them inside its write transaction; the clients
use the same rules for optimistic updates.

### Achievement integers

`achievement = round_half_even(percent × 10000)`, valid in `0..1010000`.

- Strings (`"100.5432%"`, `"100.5432"`) are parsed as exact decimals, never through a float.
- Numbers go through their shortest round-trip decimal string (JavaScript `String(n)`, Swift `"\(n)"`), then the
  string path. So the float `97.12345` and the string `"97.12345"` both give `971234` (a tie, rounded to even).
- Invalid or out-of-range input returns `null`; values are never clamped.

## Test vectors

`test-vectors/*.json` are the language-neutral source of truth for these rules. The iOS app loads them verbatim in
its Swift tests; the package's Vitest suite runs every vector too. They are exported as
`@gekichumai/maimai-domain/test-vectors/<file>.json`.

The vectors are generated by `test-vectors/generate.ts`, which spells the expectations out from the design rather
than calling the implementation. After changing a rule, update the generator and run:

```bash
pnpm --filter @gekichumai/maimai-domain vectors
```

A test fails while the checked-in JSON differs from the generator output.

### Format

Every file is a JSON object with `$comment` (a one-line summary of the contract), `version` (currently `1`; bumped
on breaking format changes) and arrays of cases. Each case has a `name` (unique within its array) except the
achievement vectors.

Conventions shared by all files:

- Achievements are integers in 1/10000 %. Absent optional values are `null`, never omitted, in expectations.
- Timestamps are ISO 8601 strings; compare them as instants (`2026-11-03T11:59:59.999+00:00` occurs).
- A **stored record** is `{achievement, comboFlag, syncFlag, dxScore, best50Bucket, providerRecordId, provenance,
  revision, deletedAt}`; `deletedAt` non-null makes it a tombstone, which keeps its last value.
- `provenance` is `{source, claimedSource, fetchedBy, verification, entryMethod, sourceAccountId, importJobId,
  rawPayloadSha256, fetchedAt, editedFromJobId}`.
- A decision's `next` is the record after the decision, `{achievement, comboFlag, syncFlag, dxScore, best50Bucket,
  providerRecordId, provenance, deleted}`, or `null` when nothing is written. Compare it field by field.

| File | Cases | Function and expected result |
|---|---|---|
| `achievement.json` | `toAchievementInt[]`: `{input, expected, note?}` | `input` is a JSON string or number; `expected` an integer or `null` |
| | `fromAchievementInt[]`: `{input, percent, formatted}` | `fromAchievementInt(input) == percent`, `formatAchievementInt(input) == formatted` |
| `score-merge.json` | `compareScore[]`: `{name, a, b, expected}` | `compareScore(a, b) == expected` (`-1`, `0`, `1`); missing flags are `null` |
| | `decideImportMerge[]`: `{name, existing, incoming, job, expected}` | `expected = {outcome, countKey, next, bumpRevision, valueChanged, liveDelta, eventKind}` |
| `manual-verification.json` | `cases[]`: `{name, existing, expected}` | `expected = {verification, editedFromJobId}` |
| `manual-mutation.json` | `cases[]`: `{name, existing, mutation, expected}` | `expected = {status, reason, next, bumpRevision, valueChanged, liveDelta, eventKind}` |

`job` is `{id, source, fetchedBy, trigger, startedAt, fetchedAt, rawPayloadSha256, sourceAccountId}`; `incoming` is
`{achievement, comboFlag, syncFlag, dxScore, best50Bucket, providerRecordId, claimedSource}`. `mutation` is
`{op: "set", value: {achievement, comboFlag, syncFlag, dxScore?}, entryMethod, basedOnRevision?}` or
`{op: "delete", basedOnRevision?}`; a missing or `null` `basedOnRevision` means baseline 0.

Enum values:

- `outcome`: `inserted`, `revived` (counted as `inserted`), `improved`, `provenanceUpgraded`, `unchanged`,
  `keptUserEdit`, `skippedDeleted`. `countKey` is the `score_import_jobs.counts` key.
- `status`: `applied`, `superseded`, `noop`, `rejected`; `reason` is set for `rejected` only
  (`invalid-achievement`, `invalid-combo-flag`, `invalid-sync-flag`, `invalid-dx-score`, `invalid-entry-method`,
  `invalid-based-on-revision`).
- `eventKind`: a `score_record_events.kind` or `null`.
- `liveDelta`: change in the save's live record count (`-1`, `0`, `1`).
